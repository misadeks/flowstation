## Property 1: AL-SETUP purge of queued DL PDUs on re-accept

- **ETSI:** Clause 23.4.4 — AL-SETUP re-establishes the link; the peer's RX window resets to N(S)=0, S(S)=0. Pre-existing DL segments carrying stale N(S) values, if delivered after the SETUP echo, will be rejected by the peer's fresh reassembler or silently wedge the session.

- **Motorola:** `dlai_cancel_pd_transmission_on_setup_req` @ 0x0021ae18 (152 bytes) — fires on every inbound AL-SETUP from an MS. Calls:
  - `dlai_remove_tma_requests_by_address` @ 0x0021ace4 (136 bytes) — evicts all queued DL MAC PDUs for this ISSI
  - `_clean_pd_user_dl_tx_state_if_needed` @ 0x0021a468 (80 bytes) — clears per-user DL TX state
  - `rm_cancel_transmission_conditional` @ 0x00238498 (60 bytes) — cancels any in-flight MAC transmission

- **flowstation:** `on_al_setup` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:1503–1533` — when `is_re_setup = self.al_links.contains_key(&key)` is true (line 1521), enqueues `SapMsgInner::TmaPurgeByAddressReq { issi: key.ssi }` to UMAC before sending the AL-SETUP echo. `reset_transfer_state()` (line 1568) then clears RX reassemblers, TX outstanding SDUs, and `next_n_s = 0`. Comment cites commit `e444a93 PD-5c-H38` and explicitly mirrors `dlai_cancel_pd_transmission_on_setup_req`.

- **Verdict:** MATCH

- **Follow-up:** accept

## Property 2: AL-RECONNECT — transfer-state reset on Propose

- **ETSI:** Clause 23.4.6 — on AL-RECONNECT Propose, the receiver confirms with Accept and resets the transfer state. Stale RX reassemblers must be cleared to prevent S(S) collisions.

- **Motorola:** No `dlai_cancel_pd_transmission_on_reconnect_req` symbol. `dlai_purge_tma_queues` @ 0x001fb7dc (64 bytes) and `dlai_purge_pd_related_queues` @ 0x001fb938 (212 bytes) exist but are not specifically linked to reconnect in the visible call graph.

- **flowstation:** `on_al_reconnect` Propose branch @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:2029–2090`:
  - Calls `link.reset_transfer_state()` (line 2042) — clears `outstanding_sdus`, `pending_sdus`, all reassemblers, `next_n_s = 0`.
  - Sends AL-RECONNECT Accept (line 2082).
  - Does **not** issue `TmaPurgeByAddressReq` — UMAC-queued segments are not evicted.

- **Verdict:** MATCH — LLC state is cleanly reset. UMAC residue is lower-risk on reconnect than on re-SETUP (typically a wider timing gap). However, see P5 for the analogous DISC path which shares the same gap.

- **Follow-up:** accept — monitor if reconnect-path stale-PDU complaints surface on hardware.

## Property 4: T.252 value and clock-start semantics

- **ETSI:** Annex A.1 — T.252 "AL acknowledgement waiting timer", recommended default 9 signalling frames ≈ 510 ms. Starts when the last segment of the SDU is transmitted; restarts on retransmission.

- **Motorola:** No explicit T252 timer symbol in the symbol table (likely a data-segment constant). `dlai_check_delay_was_exceeded_for_al_pdu` @ 0x001fa5b0 (116 bytes) handles per-PDU DL aging/expiry but its direct relationship to T.252 is unconfirmed without disassembly.

- **flowstation:**
  - **Value:** `T252_ACK_WAITING_TIMER = frames!(90)` @ `crates/tetra-pdus/src/llc/consts/timers.rs:17` — 90 signalling frames ≈ **5 s**. Comment documents iterative tuning: 9 → 30 → 90 frames, driven by MTP3550 large-SDU single-slot PDCH timing measurements (per-file comment, lines 6–15).
  - **Clock start:** `last_segment_tx_at` — set at `llc_bs_ms.rs:2190` only after every still-unacked segment reports `Transmitted` from UMAC. `sent_at` (SDU submission time) is used only for diagnostics, never for the T.252 gate (fix documented as PD-5c-H17, `llc_bs_ms.rs:143–175`).
  - **Reset on retx:** `sdu.last_segment_tx_at = None` @ `llc_bs_ms.rs:2283` — window reopens only after the retx tail actually leaves the air.

- **Verdict:** DIVERGENT-LOW — 90 frames (~5 s) vs ETSI-recommended 9 frames (~510 ms). ETSI permits operator tuning; the value is justified by measured hardware constraints. Clock-start-on-last-segment semantics are actually more correct than naive implementations.

- **Follow-up:** accept — consider exposing T.252 as a `[llc]` config knob for future tuning without a code change.

## Property 5: AL-DISC without UMAC TX purge

- **ETSI:** Clause 23.4.7 — on AL-DISC the link is torn down. No explicit UMAC purge requirement, but the practical consequence is: if the MS immediately follows DISC with a new AL-SETUP, UMAC-queued pre-DISC AL-DATA PDUs can arrive on the fresh session.

- **Motorola:** `dlai_cancel_pd_transmission_on_user_removal` @ 0x0021ad6c (172 bytes) — fires on user removal events, strongly suggesting Motorola purges UMAC queues when an MS user record is torn down. `dlai_cancel_pd_transmission_on_setup_req` @ 0x0021ae18 only fires on SETUP, not DISC. However, if DISC → new SETUP triggers the SETUP purge path, Motorola is covered regardless.

- **flowstation:** `on_al_disc` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:1633–1667`:
  - Peer-initiated: `self.al_links.remove(&key)` at line 1664. **No `TmaPurgeByAddressReq`.**
  - Own-confirm: `self.al_links.remove(&key)` at line 1652. **No `TmaPurgeByAddressReq`.**

  Critical gap: after DISC removes the link key, a subsequent AL-SETUP checks `is_re_setup = self.al_links.contains_key(&key)` (line 1521). The key is absent → `is_re_setup = false` → **the SETUP-path purge (P1) is skipped**. Pre-DISC UMAC-queued AL-DATA PDUs therefore survive into the new session.

  Concrete failure scenario: MS WAP WTP layer resets → sends AL-DISC then immediately AL-SETUP → flowstation establishes fresh N(S)=0 session → UMAC drains old N(S)=2 segments → MS reassembler receives N(S)=2 before N(S)=0 → ConflictingRetransmission or silent drop → WTP CONNECT stalls.

- **Verdict:** MATCH (via H39) — DIVERGENT-HIGH resolved 2026-07-11.
  Commit tag `PD-5c-H39` in `on_al_disc` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs`
  emits `SapMsgInner::TmaPurgeByAddressReq { issi: key.ssi }` BEFORE removing
  the link entry, on both the peer-initiated and we-initiated (own-DISC
  confirmed) branches, gated on `al_links.contains_key(&key)` so stray DISCs
  for unknown peers stay a no-op. Mirrors the H38 SETUP-side purge and the
  Motorola BRC `dlai_cancel_pd_transmission_on_user_removal` (@ 0x0021ad6c)
  behaviour. Tests: `al_disc_from_peer_removes_link` (updated),
  `al_disc_confirming_our_disc_emits_purge`, `al_disc_without_established_link_no_purge`.

- **Follow-up:** — fixed by H39.

## Property 6: AR flag on outbound DL AL-DATA segments

- **ETSI:** Clause 23.4.2 — AR bit in AL-DATA/FINAL requests immediate AL-ACK. The sender MAY set AR on any segment; not restricted to FINAL.

- **Motorola (BS→MS direction):**
  - `al_is_ar_flag_enabled_for_al_data` @ 0x00101e6c (72 bytes) — getter queried during DL MAC packing.
  - `al_disable_ar_flag_for_al_data` @ 0x00101efc (68 bytes) — **clears** the AR bit on a specific in-flight AL-DATA frame. The existence of an explicit _disable_ (vs. an explicit _enable_) implies the default is AR=1 on non-final DATA segments.
  - Companion `al_is_ar_flag_enabled_for_al_x_data` @ 0x00101eb4 (72 bytes) covers extended-AL identically.

- **flowstation (BS→MS direction):** `enqueue_al_sdu` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:2672–2678`:
  ```rust
  let config = SegmenterConfig {
      request_ack_on_final: true,   // AR=1 on AL-FINAL only
      request_ack_on_data: false,   // AR=0 on all AL-DATA
      …
  };
  ```
  `segmenter.rs:114–125` confirms: non-final → `AlDataVariant::Data` (AR=0); final → `AlDataVariant::FinalAr` (AR=1).

  **RX side correctly honours AR:** `on_al_data` @ `llc_bs_ms.rs:1678` detects `ar_flag = matches!(pdu.variant, AlDataVariant::DataAr | AlDataVariant::FinalAr)` and generates immediate cumulative ACK (lines 1732–1748) or defers to tick_end (line 1752) — this path is correct and interop-safe.

- **Verdict:** DIVERGENT-LOW — flowstation BS sends AR=1 only on AL-FINAL; Motorola BS appears to default to AR=1 on all DATA segments. ETSI-legal. Effect: one ACK per SDU vs. one ACK per segment from the MS; less UL ACK overhead but coarser partial-ACK granularity on lossy channels.

- **Follow-up:** accept — if per-segment selective retx visibility becomes a priority, expose `request_ack_on_data` as a config knob.

## Property 7: N.274 (`max_segment_retx`) negotiated but unused

- **ETSI:** Clause 23.5 — N.274 is the maximum number of retransmissions for any individual segment. Independent of the SDU-level N.273. The sender must not retransmit a segment more than N.274 times.

- **Motorola:** N.274 is negotiated in AL-SETUP; the DL packing routines (e.g., `dlai_process_tma_req` @ 0x0020bfac, 408 bytes; `dlai_pack_sdu_for_al` @ 0x001f6c3c, 220 bytes) are expected to track per-segment counts, though no per-segment-retx-counter symbol is directly visible.

- **flowstation:**
  - Negotiated and stored: `link.max_segment_retx = pdu.max_segment_retx_n274` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:1577`.
  - Validated: `sec_llc.rs:194–202` enforces 0..=15 range.
  - **Never checked at runtime.** The retransmission loop @ `llc_bs_ms.rs:2154–2338` checks only `sdu.retx_count >= link.max_sdu_retx` (line 2233). There is no per-segment retransmit counter in `OutstandingSdu` (fields: `acked_segments: Vec<bool>`, `segment_reporters: Vec<Option<TxReporter>>` — neither tracks retransmit count per segment).
  - `max_segment_retx` is **dead code** at runtime: read, stored, validated, never used.

- **Verdict:** MISSING — N.274 constraint is negotiated over-the-air but not enforced. A peer negotiating `max_segment_retx = 0` (no per-segment retx) with `max_sdu_retx > 0` (SDU-level retx allowed) will receive segment duplicates from flowstation in violation of the negotiated contract.
- **Resolved: ✅ MATCH (via H44)** — 2026-07-11: retx loop now uses `effective_max_retx = min(max_sdu_retx, max_segment_retx)` (with `max_segment_retx = 0` treated as "no per-segment retx"). Because our TX path retransmits all unacked segments together, the SDU-level `retx_count` equals the per-segment count and the combined cap correctly enforces the tighter bound. Tests: `al_tx_max_segment_retx_caps_retransmissions`, `al_tx_max_segment_retx_zero_is_fire_and_forget`.

- **Follow-up:** implement — see Draft Issue 2.

## Property 10: `al_disable_ar_flag_for_al_data` / `_prevent_packing_al_data_with_grant_before_al_ack`

- **ETSI:** No specific clause — implementation-level pacing mechanisms.

- **Motorola:**
  - `al_disable_ar_flag_for_al_data` @ 0x00101efc (68 bytes) — clears AR on a specific outbound AL-DATA. Trigger condition unknown without disassembly.
  - `_prevent_packing_al_data_with_grant_before_al_ack` @ 0x0020b8f8 (184 bytes) — prevents the DL MAC packer from emitting a new AL-DATA in the same slot as an UL capacity grant, when an AL-ACK from the MS is still pending. Purpose: avoids the BS injecting fresh DL data into a UL slot the MS has reserved for sending an ACK (half-duplex collision avoidance at the PDCH level).

- **flowstation:** No equivalent mechanism. LLC submits AL-DATA to UMAC unconditionally (no consultation of UL slot reservation state). UMAC schedules DL and UL independently.

- **Verdict:** OPEN-QUESTION — Whether this matters depends on UMAC's DL/UL scheduling. If UMAC already avoids using a reserved UL slot for DL traffic, the LLC-layer gap is harmless. Disassembly of `_prevent_packing_al_data_with_grant_before_al_ack` (≈184 bytes at 0x0020b8f8) would quantify the risk.

- **Follow-up:** investigate — disassemble and determine whether flowstation UMAC handles the equivalent timing constraint.

## Property 12: `retx_count` off-by-one vs N.273

- **ETSI:** Clause 23.5 — N.273 is the maximum number of **retransmissions** (not total transmissions). With N.273 = 3: up to 4 total transmissions (1 initial + 3 retx).

- **Motorola:** No directly comparable symbol; N.273 semantics presumed standard.

- **flowstation:** `submit_al_activity_to_umac` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:2230–2332`. Trace with `max_sdu_retx = 3`:

  | Iteration | `retx_count` at entry | Gate `>= max_sdu_retx` | Action | `retx_count` at exit |
  |---|---|---|---|---|
  | 1 (initial send) | 0 | 0 ≥ 3 → false | send | 1 (line 2331) |
  | 2 (1st retx) | 1 | 1 ≥ 3 → false | retx | 2 (line 2285) |
  | 3 (2nd retx) | 2 | 2 ≥ 3 → false | retx | 3 |
  | 4 (3rd retx attempt) | 3 | **3 ≥ 3 → true** | DROP | — |

  Result: 1 initial + **2** retransmissions. ETSI N.273 = 3 permits **3** retransmissions (4 total). flowstation exhausts the budget one retransmission early. Edge cases: N.273 = 0 (`0 ≥ 0` true on iteration 2, correct fire-and-forget) and N.273 = 1 (`1 ≥ 1` true on iteration 3: 1 initial + 1 retx = correct) behave correctly. The off-by-one only affects N.273 ≥ 2.

- **Verdict:** DIVERGENT-LOW — Delivers `max_sdu_retx − 1` retransmissions for N.273 ≥ 2. ETSI-legal (it is a maximum, not a minimum). On-air impact: minor; BS gives up one attempt earlier than permitted. Fix: change gate to `>= max_sdu_retx + 1` (or restructure counter to 0-based with 0 = "not yet sent").
- **Resolved: ✅ MATCH (via H44)** — 2026-07-11: fixed by distinguishing "initial send from buffered state" (`sdu.sent_at.is_none()`) from a real retransmission. Only real retx now burns budget or increments `retx_count`. With N.273 = 3 the SDU is retransmitted exactly 3 times before drop. Test: `al_tx_retx_count_matches_n273_no_off_by_one`.

- **Follow-up:** implement — low-risk one-line fix, reduces unnecessary SDU drops on lossy channels.

## Draft issues (HIGH-impact only)

### Issue draft 1: AL-DISC does not purge UMAC; post-DISC AL-SETUP sees stale PDUs

- **Symptoms:** After a clean AL-DISC followed immediately by AL-SETUP (e.g., WAP WTP layer reset, MS soft-reboot), UMAC may still have pre-DISC AL-DATA PDUs queued for the peer. These arrive at the MS after its fresh N(S)=0 session starts, are silently dropped or trigger a ConflictingRetransmission error in the MS reassembler. If the MS is expecting N(S)=0 to confirm WTP CONNECT, it never receives it cleanly; the WAP stack retries indefinitely (~11 s delay per observed MTP6550 hardware trace, analogous to the pre-P1 SETUP loop).

- **Reproduction:** While a multi-segment DL AL SDU is mid-transfer (multiple AL-DATA segments already queued in UMAC), have the MS send AL-DISC then immediately AL-SETUP. Confirm whether stale pre-DISC N(S) segments arrive on the new session.

- **Reference:** ETSI clause 23.4.7 (DISC tears down link). Motorola `dlai_cancel_pd_transmission_on_setup_req` @ 0x0021ae18 purges on SETUP; analogous teardown exists for user-removal @ `dlai_cancel_pd_transmission_on_user_removal` @ 0x0021ad6c. flowstation `on_al_disc` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:1633–1667` — no `TmaPurgeByAddressReq`. P1 guard @ `llc_bs_ms.rs:1521` skips purge because link key is absent after DISC.

- **Suggested fix path:**
  - **Option A (simplest):** In `on_al_disc`, before `self.al_links.remove(&key)`, issue `TmaPurgeByAddressReq { issi: key.ssi }` — mirrors P1 fix identically.
  - **Option B:** Change `is_re_setup` in `on_al_setup` to also fire when the link was recently removed (e.g., track a per-SSI "last-disc-time" in LLC and purge if the gap is below one multiframe). More complex, less clean.
  - Option A is preferred.

### Issue draft 2: N.274 (`max_segment_retx`) is negotiated but never enforced

- **Symptoms:** A peer that negotiates `max_segment_retx_n274 = 0` (no per-segment retransmission) with `max_sdu_retx > 0` (SDU-level retx allowed) will still receive retransmissions of every unacked segment from flowstation on T.252 expiry, violating the negotiated contract. The peer may interpret duplicate segments as a protocol error, log CRC-pass duplicates, or fail to reassemble correctly if its reassembler rejects ConflictingRetransmission variants.

- **Reproduction:** Use an AL simulator that negotiates `max_sdu_retx = 2`, `max_segment_retx = 0`. Induce a segment loss (drop one AL-DATA at the simulated MAC level). Observe whether flowstation retransmits the dropped segment (violates N.274 = 0) or drops it and attempts a full-SDU retransmission instead (correct).

- **Reference:** ETSI clause 23.5 (N.274 definition). flowstation `AlLink::max_segment_retx` @ `crates/tetra-entities/src/llc/llc_bs_ms.rs:202` — stored but never referenced. Retransmit loop @ `llc_bs_ms.rs:2156–2338` — checks only `link.max_sdu_retx`.

- **Suggested fix path:**
  1. Add `pub segment_retx_counts: Vec<u8>` field to `OutstandingSdu` (indexed by S(S)).
